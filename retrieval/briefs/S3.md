## What must be true

### F-1a — exactly one embedder for the whole index

The manifest records **one** model id and **one** revision. A build that would
mix embedders — appending to an index built by a different model, or a
different revision of the same model — must **fail loudly**, not silently
produce a mixed index whose cosines are meaningless. Test that failure path
explicitly; it is the whole point of F-1a.

Every crop is resized to the model's native input, so a 112 px crop and a
448 px crop cost the same forward pass. That is expected, not a bug.

### F-2 — unit-normalised vectors, with provenance

- `||v||_2 = 1.0 ± 1e-5` for **every** tile. Assert over the whole index, not a
  sample.
- Dimensionality **768**.
- Each vector records its `tile_id`, **scale**, and the model id + revision.
- Store fp16 on disk (fp32 is wasted here); assert the norm **after** the
  round-trip through fp16, not before, since that is what later stages load.

### N-2 — an unattended, resumable build

- Runs to completion with no human intervention.
- Logs **tiles/sec and total wall time** at the end. Compare against S0's
  265 tiles/sec and say if you are far off.
- **Resumable after interruption without re-embedding completed tiles.** Test
  this for real: kill a build partway, restart it, and assert the finished
  index is identical to an uninterrupted one *and* that the second run embedded
  strictly fewer tiles than the first. A resume that silently re-embeds
  everything passes a naive test and fails this one.

### N-4 — determinism

The same tile bytes produce the same embedding to within **1e-5** across runs
on this device. Fixed seeds; record the model id and revision alongside the
vectors.

## One decision the PM has made for you — nodata tiles

`X605_Y3388` is **14.2% zero-fill**. Its plan marks per-tile nodata fractions.

**Embed every tile that contains at least one real pixel. Skip only tiles that
are 100% nodata.** Record `nodata_fraction` per tile in the index.

*Why this and not the planner's >50% "valid" rule:* cost is not the constraint
— the whole AOI is 42 seconds, so skipping tiles saves nothing worth having.
The real risk is the opposite: a wholly-blank tile is a uniform black square
that will rank highly for queries like "shadow" or "dark", polluting results
with content that does not exist. A tile that is 60% nodata still contains 40%
real imagery and may hold the only car in that corner. So exclude only what
carries literally zero information, and let later stages filter on the recorded
fraction rather than discarding data now.

Report both counts: tiles planned, and tiles embedded.

## Constraints

    AERIAL_DATA_ROOT=/home/omer/PycharmProjects/Dynamic-Terrain/data \

**Your Bash tool does not persist env vars between calls — prefix every python
and pytest invocation inline, every time.** Without `PYTHONNOUSERSITE=1` the
build silently runs on **CPU at ~5 tiles/sec instead of 265** and still appears
to work. If your throughput is ~50x low, that is the cause — not the hardware.

- **dtype comes from `src/device.py`.** Do not hardcode `float16`. This machine
  is cc 7.5 so it resolves to fp16, but that is a case of the rule.
- **Paths come from `src/config.py`.** N-8 forbids machine paths anywhere in
  `src/`, docstrings included, and `tests/test_portability.py` greps for them.
- **Tile ids via `posix_key()`**, so a Linux-built index matches a Windows one.
- **The data directory is READ-ONLY.** All output under the index root. If you
  need a RED for a write-guard, aim it at a **scratch stand-in**, never the real
  data root.
- Never commit weights, tiles or embeddings.
- All **79** existing tests stay green.
