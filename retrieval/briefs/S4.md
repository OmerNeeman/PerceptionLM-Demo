## What already exists — do not rebuild it

`load_index(aoi, index_root=None, renormalize=True)` returns the AOI's vectors
**already renormalised to unit norm** (max deviation 1.19e-7). fp16 on disk
cannot hold unit norm to 1e-5 — that is settled and amended; **do not
re-litigate it, and do not disable `renormalize`** for ranking. Raw stored norms
vary 0.9997-1.0003, so an un-renormalised dot product is **not** a valid cosine
across tiles.

Manifest: `model_id`, `revision`, `dim` 768, `scales` [448,224,112],
`batch_size` 256, `planned_count` 11109, `tiles` (9,631 records of
`tile_id` / `scale` / `nodata_fraction`), `skipped_tile_ids` (1,478).

## The trap — tile ids encode GRID INDICES, not pixel offsets

`X605_Y3388::X605_Y3388.tif::unknown::448::00012::00000` is
`aoi::source::date::scale::col_index::row_index`. **Pixel offset = index x
scale.** The PM lost time to this: reading at `(12, 0)` returns solid black
while the manifest correctly reports zero nodata.

**F-10 requires every result to carry its map location.** Get geo by **joining
to `index/tileplan/*.json`** (S2, which owns footprints and lat/lon boxes) — do
**not** re-derive geometry from the id string. If the join needs a key the plan
does not expose, add a lookup in `tiling.py` rather than parsing ids here.

## F-4 — ranking is PER SCALE. Owner decision, not a preference.

Return **one ranking per entry in `SCALES`**, each labelled with its **true
ground extent** — 448 -> 44.8 m, 224 -> 22.4 m, 112 -> 11.2 m for this UTM AOI
(use `geo.py`; do not hardcode, and note `leb` differs at 46.91/23.46/11.73 m).

Never a single pooled ranking. Measured reason: 112 px takes top-1 for 9/9
queries, so pooling buries every scene-level query. An 11.2 m crop physically
cannot contain a road as a linear object.

`TOP_K` means top-`TOP_K` **per scale**. Scores are only ever compared **within**
a scale.

## U-3 — the weak-match signal is a RELATIVE gap

No absolute cosine cut-off is usable. Implement: a query is **weak** when its
top score fails to exceed that scale's corpus mean by a stated multiple of the
score spread. Put the mechanism here; S5 renders it.

Calibrate against real measurements the PM took on this exact index (112 px
top-1): `tents` +0.2805 · `palm trees` +0.2801 · `a car` +0.2650 ·
`dirt road` +0.2571 · **`aircraft carrier` +0.2332 (known-absent)**. Your rule
must flag the control and not flag the four real queries. **State the multiple
you chose and show it separates these six cases.** Do not tune it to only just
work — report the margin.

## F-2a — measure the PCA cost, per scale

Fit PCA to `EXPORT_DIM` = 128 on the indexed corpus, then int8. Store the basis
so a query vector projects identically at query time.

**Report retrieval@10 overlap between full-precision and exported embeddings —
per scale, not pooled.** A single number would hide a scale-specific loss, and
112 px is where the small objects live. Use a query set of at least the six
above. **This must be a number, not an assumption** — the owner asked for it
specifically. If it is bad, say so; that is a finding, not a failure.

## The rest

- **F-3:** query text through the **same model's** text tower; `||q|| = 1.0 ±
  1e-5`; identical text gives a bitwise identical vector in-process and within
  1e-6 across processes.
- **F-5:** reload in a fresh process gives **byte-identical** top-`TOP_K` ids and
  scores; reload completes in **< 5 s**.
- **F-6:** lat/lon bbox filter; a bbox covering one known tile returns that tile
  and no other; an empty bbox returns nothing and **does not raise**. Note S2's
  finding: UTM tiles' lon/lat boxes are **not bit-exact at shared edges**
  (~0.26 m, meridian convergence) — do not assume bit-exact adjacency.
- **N-1:** top-10 over the full index in **< 200 ms on CPU**. Measure and paste.
  numpy exact brute force; **no faiss, no sklearn wrapper** (measured 68x
  slower), no Python loop over tiles.
