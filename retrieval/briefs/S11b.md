# Brief — S11b: model selector + side-by-side comparison

**Dispatch:** subagent. **Depends on:** S11a (both indexes built).
**Proves:** F-1a in the UI, F-4 unchanged, N-1 unchanged.

## Goal

Let the user **choose which model searches**, and see both answer the **same
query on the same imagery, side by side**.

## The constraint that shapes everything

**Scores from different models are not comparable.** Different spaces,
different score scales. RemoteCLIP's `+0.2650` and PE Core's `+0.31` mean
nothing against each other.

So:

- **Never merge, interleave or jointly rank results from two models.**
- **Never show a single "which won" verdict** computed from raw scores.
- Comparison is **ranked content side by side** — same query, same scale, two
  columns, each labelled with its model and dimensionality.
- If you show a per-model number, it must be **within-model**: that model's own
  confidence band against its own background set.

This is F-1a expressed in the UI. Getting it wrong produces a comparison that
looks authoritative and means nothing.

## What to build

1. **A model selector** beside the existing AOI and date filters. Switching
   re-runs the current query against that model's index. Default stays
   **RemoteCLIP** — it won S0 and is the shipped default.
2. **A compare view**: one query, both models, results in two columns per scale
   row. Each column headed with the model id and dim (`RemoteCLIP-ViT-L-14 ·
   768-d`, `PE-Core-L14-336 · 1024-d`).
3. **U-6 applies:** the active model is visible with the result count it
   produced, and clearable/resettable in one action like the other filters.
4. Keep everything already right: per-scale rows with true ground extent, the
   resolution caveat, confidence bands worded "may not be present", the tile
   modal, the date control for `leb`.

## Memory — check before you build

Both indexes resident is **104,374 x 768 fp32 + 104,374 x 1024 fp32 ≈ 750 MB of
vectors** before overhead. RSS with one index was already **1,419.6 MiB**.

**Measure it.** If holding both is unreasonable, load the second lazily on first
use and say so — do not silently double the footprint. Report peak RSS with
both loaded.

## N-1 still applies

Top-10 in **< 200 ms on CPU** per model. Currently 65.7 ms at full scale with
768-d; 1024-d is ~33% more arithmetic. Measure both. A compare view runs two
queries, so report that total too.

**If either breaches 200 ms, flag it** — do not reach for an approximate index,
which `spec.md` §7 excludes by explicit decision.

## Acceptance criteria — test-first, paste RED then GREEN

- `test_model_selector_switches_index` — querying under each model reads that
  model's index; ids come from the right corpus
- `test_no_cross_model_merging` — no code path concatenates or jointly sorts
  vectors or results from two models
- `test_compare_view_same_query_both_models` — both columns are the same query
  and the same scale, each labelled with model and dim
- `test_query_latency_per_model` (N-1) — both under 200 ms on CPU, measured
- All existing tests green.

Then **use it as an impatient user**: switch models mid-query, switch AOI while
in compare view, compare on a known-absent query, and switch to a model whose
index is missing for that AOI (if any). Nothing may show a stack trace.
