# Brief — S2: tile planner + geo round-trip

**Dispatch:** subagent (metadata-only planning + two COG conversions; no GPU,
no weights).
**Proves:** spec **F-1**, **F-10**, **D-3**, **D-4**.
**Depends on:** S1 (`src/inventory.py`, `src/geo.py`).

## Goal

Two things, both metadata-first:

1. A **tile planner** that lays a padded grid over every indexable scene at
   every scale in `SCALES`, with stable ids and exact geographic footprints.
2. **COG copies of `leb`'s two scenes only**, so interactive window reads stop
   costing ~45x read amplification.

The planner reads **no pixels** to produce a plan. A plan is pure arithmetic
over dimensions and geotransforms, so planning all 8 scenes is nearly free —
do that, and assert the totals. Pixel reads enter only for nodata validity and
for the COG conversion.

## The tile-count arithmetic — verified by the PM, use it, do not re-derive

`SCALES = [448, 224, 112]`, `OVERLAP = 0.0`. **Edge tiles are padded to full
size, never dropped** — dropping the 376 remainder rows at 448 px would lose
3.8% of scene height. So the grid is `ceil(W/s) x ceil(H/s)`.

The PM recomputed all of these from the scene dimensions in `docs/DATA.md` and
they are exact:

| scale | grid per 10240² scene | grid per `leb` scene (20179x9784) | all 8 scenes |
|---|---|---|---|
| 448 | 23 x 23 = 529 | 46 x 22 = **1,012** | **5,198** |
| 224 | 46 x 46 = 2,116 | 91 x 44 = 4,004 | **20,704** |
| 112 | 92 x 92 = 8,464 | 181 x 88 = 15,928 | **82,640** |
| | | | **108,542** |

`X605_Y3388` alone (the demo AOI): 529 + 2,116 + 8,464 = **11,109**.

Assert these exactly. They are not estimates.

### Two different tile-count conventions exist in our docs — do not conflate them

This is the trap in this stage, and it will silently produce a wrong test.

- **F-1's 108,542 is the PADDED PLANNED grid**: `ceil`, all 8 scenes, nodata
  ignored. This is what the planner must produce and what you assert.
- **`docs/DATA.md`'s "448 tiles (valid)" column is something else**: `floor`
  (complete tiles only, no padding) **and** reduced by nodata — which is why
  `X693_Y3501` shows 352 rather than 484 (25.1% zero-fill) and `X605_Y3388`
  shows 397 rather than 484 (14.2%).

Both concepts are legitimate and you need both: the **plan** (every grid cell)
and the **valid subset** (cells with real pixels). Keep them as separate,
separately-named fields. Never let one stand in for the other.

**A known error, already found by the PM — do not treat it as your finding and
do not silently match it:** `docs/DATA.md`'s per-scene column sums to **4,575**
but the file states a total of "**~4,146**", an unexplained gap of 429. Your
measured valid-tile counts settle it. Report your numbers; the PM corrects the
manifest. If your valid counts disagree with that column per scene, say so with
the nodata fraction you measured.

## F-1 — coverage, exactly

- For each scale independently, **every pixel of the raster falls in at least
  one tile** of that scale. Assert **zero coverage gaps**, not just the count —
  a correct count with an off-by-one origin can still leave a seam.
- Assert exact per-scale counts against the table above.
- Padding: state and test what pad value is used, and record per tile the
  **valid (unpadded) pixel region**, so a later stage can tell a real edge tile
  from a full one.

## F-10 — every tile carries its map location

- Each planned tile records: `tile_id`, source file, date, scale, pixel offsets
  `(col, row)`, pixel size, and its **lat/lon bbox** (EPSG:4326).
- **Round-tripping a tile id through the geotransform reproduces its pixel
  offsets exactly** — that is the test, and it must hold for both CRSs.
- The two CRSs are the point here: `leb` is **EPSG:3857**, the six others are
  **EPSG:32636**. Both must yield correct lat/lon. Reuse S1's `geo.py`; do not
  reintroduce the GSD trap or apply the Mercator cosine correction to a UTM
  scene.
- `pyproj.CRS` and `pyproj.Transformer` are **broken in this env** (no PROJ
  database — `CRSError: no database context specified`). Route CRS work through
  **rasterio/GDAL**. `pyproj.Geod` works, being pure ellipsoidal geodesy. S1
  already hit this; do not rediscover it.

## D-4 — tile identity is stable

A tile id derives from `(aoi, source_file, date, col, row, TILE_PX)`.
*Expected:* two planning runs over unchanged inputs produce **identical ids and
identical counts**. No filesystem-iteration order dependence, no timestamps, no
absolute paths inside the id. Note that five of the eight scenes have
`date: unknown` — the id scheme must handle that without collapsing two scenes
into one id, and without embedding a build-time value.

## The COG conversion — `leb` only

`leb`'s two scenes are **20179 x 1 strips with no overviews**: a random 448²
RGB window costs ~27 MB of I/O to return 0.6 MB of pixels, ~**45x**
amplification. The other six scenes are already tiled 256x256 (~2.9x) and
**must not be converted** — that would be hours of wasted work.

- Output to `index/cog/`, **never in place**. The source files are read-only.
- Assert the COG is pixel-identical to its source over at least a few sampled
  windows, and that its CRS, geotransform and band count are preserved. A COG
  that silently resamples or reprojects would corrupt every downstream
  embedding while looking fine.
- Report the measured read-amplification improvement for a 448² window,
  before and after. That number is the entire justification for the stage.

## UX expectations

No user interface, but the plan is read by humans when a build goes wrong:

- The per-scene summary states planned count, valid count, and nodata fraction
  per scale — so "529 planned, 397 valid, 14.2% nodata" is visible without
  parsing JSON.
- The COG step reports before/after read amplification for a 448² window.
- A tile record is self-describing: someone reading one JSON entry can locate
  that tile on a map and in the source raster without consulting code.
